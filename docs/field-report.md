# 实测报告：33.75 GB 夸克下载与 CDN 412 风控

> 2026-11-14，真实一次从夸克网盘分享下载 33.75 GB 单文件（RAR5 压缩包）的完整记录。
> 本报告的所有数字都来自当场实测，不是推测。

## 背景

- 分享链接：`https://pan.quark.cn/s/YOUR_PWD_ID`
- 文件：`Gujian3.rar`，36,236,559,549 字节（33.75 GB）
- 账号网盘容量仅 10 GB，无法转存，只能走直链下载

## 第一道坎：TLS 指纹

夸克的直链（`dl-pc-zb.drive.quark.cn`）由阿里 Tengine + ENS 边缘节点提供，**按 TLS 指纹拦截**：

| 客户端 | 结果 |
|--------|------|
| Python `urllib` | 412 |
| Python `requests` | 412 |
| Windows BITS | 失败 |
| **Windows 自带 `C:\Windows\System32\curl.exe`** | **206 成功** |

Windows 的 curl 走 Schannel（Windows 原生 TLS 栈），指纹和浏览器/客户端接近，能过。

**这是整个项目必须用 `subprocess` 调 curl、而不是用 Python HTTP 库的原因。**

## 第二道坎：412 是概率性的

拿到直链后第一次测试，同一个 URL 连打 20 次：

```
206, 412, 412, 206, 412, 412, 412, 206, 206, 412,
412, 412, 412, 206, 412, 412, 206, 412, 412, 412
```

**6/20 = 30% 命中率。** 关键观察：

- 命中 412 只花约 **0.4 秒**，成本极低
- 成功的请求响应头里 `Via` 都带 `cache13.l2cn7478[0,0,304-0,H]`（走 L2 缓存回源）
- 失败的只有 `ens-cacheXX.cn8142[,412666]`（边缘节点直接拒绝）
- **每次刷新新直链，命中率没有提升**（15 次测试 5 次成功，同样约 30%）

结论：**不是 URL 失效，是边缘节点的调度/缓存问题。刷新 URL 无用，重试才是解。**

## 第三道坎：412 会随时间急剧恶化

这是最坑的一点。30% 命中率并不是稳态。

### 时间线

| 时间 | 状态 | 412 命中率 | 备注 |
|------|------|-----------|------|
| 21:11 | 正常 | ~30% | 256 MB 大分块也能成（第 5 次尝试成功） |
| 21:28 | 下载中 | 较高 | 540 块中 521 块顺利下完 |
| **22:10** | **急剧收紧** | **~0%** | 1/4/16/64 MB 全部几乎 100% 412 |
| 22:25:41 | 窗口恢复 | 正常 | 19 个缺失块 70 秒内补齐 |

### 22:10 那次恶化时的实测数据

用修正后的正确单位（MB，不是字节）重测：

| Range 大小 | 同 URL 连打 20 次 | 每次刷新 URL 打 10 次 |
|-----------|------------------|---------------------|
| 1 MB | 0/20 (0%) | — |
| 4 MB | 0/20 (0%) | 0/10 (0%) |
| 8 MB | 1/20 (5%) | — |
| 16 MB | 0/20 (0%) | 0/10 (0%) |
| 64 MB | 0/20 (0%) | 0/10 (0%) |

对照实验全部无效：
- 换 Chrome UA → 412
- 去掉 Referer → 412
- 去掉 Cookie → 412
- HTTP/1.0 → 412
- 低偏移对照块（之前成功过的 chunk 250）→ 3/3 全 412

**所以既不是"高偏移专属"，也不是 Cookie 过期，也不是脚本 bug。是整体风控收紧。**

### 触发条件推测

累计下载约 **30 GB** 之后开始收紧。这符合按流量/累计请求量触发的风控模型。

值得注意的是：**这个收紧是临时的**。22:25 左右窗口自行恢复，说明不是永久封禁。

## 架构怎么设计的

基于上面三条规律，最终架构是：

### 1. 分块

64 MB 一块，540 块。分块的理由不是"太大下不动"，而是：
- 某一块彻底失败时，只损失 64 MB 的重试成本
- 天然支持断点续传
- 小 Range 在风控期相对更容易钻过去（22:07 曾有 4 MB 子段 21:xx 时拿到 206）

### 2. 强校验（血的教训）

**第一代脚本用 `curl -C -` 断点续传，结果出了大事：**

CDN 返回 412 时，响应体是一个 262 字节的 HTML 错误页。`curl -C -` 把它当成"已下载的进度"追加进了分块文件。于是：

- `part00` 前 262 字节是 `<!DOCTYPE HTML...>`
- 其后 1 GB 数据**整体偏移了 262 字节**
- 文件看起来"长大了"，进度看起来"在涨"，实际全是废数据

白下 2 GB 才发现。

**修正后的强校验：一个块必须同时满足全部四条才算完成**

```python
code == '206'                          # HTTP 状态
and size == want                       # 下载字节数精确相等
and content_range == 'bytes %d-%d/%d'  # 响应头区间精确匹配
and not has_html_marker(file)          # 全文扫描无 <!DOCTYPE / 412 Precondition
```

只有全过才 `os.replace(tmp, final)`。任何一条不过就删掉重来。

**永远不要用"curl 退出码 0"或"文件变大了"判断成功。**

### 3. 低频探针等窗口

22:10 那次，19 个块各重试 80 次全 412。继续硬刷只会让风控更紧。

改成：

```
每 45 秒发 1 个 4 MB 探针请求
  ├─ 412 → 继续等，不加剧风控
  └─ 206 → 窗口开了！立刻 6 并发补齐所有缺失块
```

实测：22:25:41 探针发现窗口，19 块在 70 秒内全部补齐（多数 try=1~3）。

**关键：探针频率必须低。高频轮询是在给风控喂数据。**

## 性能实测

| 指标 | 数值 |
|------|------|
| 单连接速度 | 1.3 ~ 2.4 MB/s |
| 8 并发聚合（冷启动） | 9.05 MB/s |
| 8 并发聚合（缓存热） | 15.4 ~ 30 MB/s |
| 540 块下载总耗时 | 约 38 分钟 |
| MD5 计算耗时 | 73.7 秒（33.75 GB，约 466 MB/s） |

并发确实能叠加带宽，8 路是实测比较稳的点。

## 校验的坑：不要信夸克 API 的 md5 字段

下载完成后：

- 本地整文件 MD5：`aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa`
- 夸克 download 接口返回的 `md5`：`bbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbb`

**对不上。** 但文件其实是完好的：

1. `UnRAR.exe t -inul` 全量 CRC 测试 → **退出码 0**（RAR5 每块带 CRC32，错一字节必报错）
2. 抽样 5 个位置（0 / 1 GB / 12 GB / 24 GB / 34.5 GB），与远端重新拉取的数据**逐字节比对全部一致**

结论：那个 `md5` 字段不是整文件哈希（可能是分片哈希、旧版本哈希，或别的东西）。**拿它校验会误判成下载损坏，然后白白重下 33 GB。**

正确的校验顺序：

1. 大小精确相等
2. 文件魔数正确
3. **压缩包 CRC 全量校验**（最权威）
4. 抽样与远端逐字节比对

## 另一个 bug：脚本自身的校验切片写错

最后合并完成时脚本报了 `DONE ok=False`，差点以为失败：

```python
ok = (size == TOTAL and head[:4] == b'Rar!\x1a\x07')
#                        ^^^^^^^^ 4 字节
#                                  ^^^^^^^^^^^^^ 6 字节常量
```

`head[:4]` 是 4 字节，拿去比 6 字节常量，**恒为 False**。

正确写法：`head[:6] == b'Rar!\x1a\x07'` 或 `head.startswith(b'Rar!\x1a\x07')`。

教训：**校验代码本身也可能有 bug。当校验报失败但各项人工检查都正常时，先怀疑校验代码。**

## 环境相关的坑

### 后台进程存活

在 DSH / Electron 类宿主里，用 Node 的 `spawn({detached: true})` 启动的子进程会被宿主的 job object 回收——**进程立刻消失，日志全空**。

必须用 ShellExecute 类方式（本项目测试环境里是 `computer_launch`）启动，才能真正脱离父进程存活。

### WSL 不可用

这台机器装了 WSL 组件但没装发行版，`wsl.exe` 任何命令都返回 `WSL_E_DISTRO_NOT_FOUND`。所以 shell 脚本一律走 PowerShell / cmd。

## 一句话总结

**这套东西真正的难点不是"怎么下"，是"怎么确认下对了"。**

412 好破（重试 + 等窗口），但错误页污染数据、API 的 md5 字段不可信、自己的校验代码写错，这三件事任何一个都能让你以为成功了、实际白干，或者以为失败了、实际白删。

强校验 + 压缩包自带 CRC，是唯一靠谱的终点判断。
